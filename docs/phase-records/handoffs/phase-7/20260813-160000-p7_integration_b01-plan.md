## Additive persistence and provenance contract

Generate the one ordered Drizzle migration and metadata from the final schema; do not hand-edit a
second divergent migration. Existing rows must migrate without a fabricated system principal.

1. `settings_versions.reset_buffer_minutes` is a non-null PostgreSQL integer with default `30` and
   a nonnegative constraint. It is mapped only into reset evaluation settings. The frozen schema-v2
   edge response intentionally still omits it.
2. Keep authentication principal kinds and roles exactly `shared_staff | owner` and
   `staff | owner`. Introduce a database `command_issuer_class` of `human | system` plus a
   separate audit actor representation that can express `system` without adding a login principal
   or role:
   - migrate `audit_log.actor_principal_kind` to a dedicated audit actor enum
     `shared_staff | owner | system`;
   - add `audit_log.command_issuer_class`, make actor principal ID and role nullable only for
     `system`, and constrain `human` rows to their existing FK-backed kind/role pairs while system
     rows are `system` with null principal/role;
   - add `edge_commands.issuer_class`; make `issued_by_principal_id` nullable only for `system` and
     require it for `human`. Existing rows migrate as `human`; system commands have no principal
     FK value;
   - add a unique referenced command identity `(id, issuer_class, type)` and make audit reference
     `(command_id, command_issuer_class)` through a matching unique command `(id, issuer_class)`.
     This makes both human-audit/system-command and system-audit/human-command raw SQL inserts fail,
     not merely application validation.
4. Add `scheduled_reset_issuances` with one row per business day and stable issuance key. It stores
   business day, `scheduled-reset:<ISO-date>` key, owning settings version FK, scheduled close,
   due time, command FK, and issued time. Its constant `command_issuer_class = system` and
   `command_type = reset_zero` are check-constrained and participate in a composite FK to the
   command's `(id, issuer_class, type)`, so a claim cannot reference a human or non-reset command.
   Business day, issuance key, and command are unique; due is not before close; issued is not before
   due. This row is the durable close/claim marker and is not deleted or reopened when its command
   becomes applied or superseded.

Migration tests inspect the resulting constraints and prove existing human command/audit fixtures
retain identical semantics. Raw SQL attempts for both audit/command issuer mismatch directions, a
scheduled claim referencing a human or non-reset command, actor/issuer incoherence, or a duplicate
business day must fail.

## Deep command and scheduled-reset module

Extend the internal command service, not any product-facing route:

- human correction/reset entry points and their public types/behavior remain unchanged;
- add one internal `issueScheduledReset(decision)` method accepting only the typed issue decision
  produced by the reset evaluator;
- in the existing command transaction, lock the singleton/active device, re-check the durable
  business-day issuance, insert a system `reset_zero`, supersede older pending commands, append a
  system reset audit, and insert the scheduled issuance before one commit;
- a repeated/concurrent decision whose business day already exists returns the existing claim as
  already issued without inserting, superseding, or auditing anything;
- unique-constraint races are resolved as idempotent only after reading the exact existing
  business-day claim; no unrelated constraint or database failure is swallowed;
- missing/changed device, audit failure, claim failure, or any injected fault rolls back issuance,
  command, supersession, and audit together.

The system audit records action `reset`, prior current value (nullable when unavailable), requested
and effective value `0`, the evaluator's stable reason, and exact issuance time. It is attributable
to `system`, not staff/owner. Issuing a command never mutates cloud current occupancy; only the
accepted edge acknowledgement path later does so.

`reset/runner.ts` is the single orchestration seam. At one injected `now` it loads all append-only
settings versions and existing scheduled issuances, derives a small deterministic set of candidate
ISO business days from each version's local civil date at `now` and at
`now - resetBufferMinutes` (including adjacent dates needed for past-midnight/boundary attribution),
sorts/deduplicates them, evaluates each through `evaluateScheduledReset`, and passes only `issue`
decisions to `issueScheduledReset`. It never recomputes close, buffer, due time, ownership, or
already-issued behavior itself. Candidate generation is independent of settings row order and is
tested at exact due and on a later cron invocation within the following civil day. Repository
completion does not promise catch-up after a multi-day cron outage; minutely production cadence is
an external deployment prerequisite explicitly flagged by the spec.

The database reader orders full settings history by `effectiveFrom`, then version, maps weekly
schedule and `resetBufferMinutes`, and joins issuance rows to current command status for evaluator
input. No latest-settings substitution is allowed.

## Cron transport and security contract

`CRON_SECRET` is validated as a non-empty secret of at least 32 characters. Tests set a synthetic
value before importing the env-bound app; no real value is committed, printed, or copied into a
handoff.

`createCronHandler` receives injected secret, clock, and runner. It accepts GET only through the
mounted Hono route, requires exactly one `Authorization` header in canonical `Bearer <secret>`
form, compares fixed-length SHA-256 digests with timing-safe equality, and returns the same 401 body
for missing, malformed, short, or wrong credentials before invoking the runner. It never accepts a
query/body secret and never logs credentials. A valid call runs once and returns a fixed 200 body;
an unexpected runner error returns a fixed 500 category while preserving server-side error-name-only
diagnostics.

`createApp()` mounts internal `/cron` outside oRPC. The root Vercel schedule calls `/api/cron`, whose
existing rewrite strips `/api` for the server. The route has `Cache-Control: no-store`; request logs
contain only method/path/status and no authorization value. No browser or user session can
substitute for the cron bearer.
