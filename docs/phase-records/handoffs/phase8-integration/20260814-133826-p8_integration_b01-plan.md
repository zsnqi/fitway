## Retention referential-integrity constraint (binding)

`alert_log.recovery_of_alert_id` is a self-referencing foreign key
(`packages/db/src/schema/application.ts:524-526`). A condition that opened before the retention
cutoff and recovered after it produces an **expired parent row still referenced by a retained child
row**. A naive `delete ... where sent_at < cutoff` violates that constraint.

Retention must therefore preserve referential integrity: an `alert_log` row that is still referenced
by any row being retained is itself retained, regardless of age. Note also that the accepted
evaluator design appends **two** rows per notice — a durable `claimed` row inside the transaction
and a `delivered`/`failed` outcome row afterwards (`alert-repository.ts:218-244`) — so retention
arithmetic and its tests must count rows, not notices.

`audit_log` and `edge_health_log` are referenced by no other table, so their deletion is
unconstrained. `audit_log` is itself a child of `edge_commands` through the composite foreign key
`audit_log_command_issuer_fk` (`packages/db/src/schema/application.ts:425-429`, declared with
`foreignKey()` rather than the inline `.references()` form used elsewhere in that table); deleting
an audit row does not violate that direction. `edge_commands` is not a retention target, so that
key is never stressed by this slice.

## Disclosed adjudications (a human may overrule; none blocks activation)

1. **Alert policy constants, not settings columns.** `evaluateAlerts` requires `preOpenWindowMs` and
   `reAlertIntervalMs` as caller-supplied policy (`packages/api/src/alerts/types.ts:21-28`).
   `settings_versions` has no such columns (`application.ts:116-153`). `SPEC.md:595-598` freezes both
   values at 30 minutes and marks them `[Resolved here — defaults]`; `SPEC.md:532` scopes the
   settings table to "timezone, hours, capacity, thresholds", which does not include alert policy;
   and `PHASES.md:275-276` gives `phase11-settings` capacity, thresholds, schedule, business-day,
   reset, and freshness — again not alert policy. This slice therefore supplies both as frozen named
   constants at the composition boundary. That requires no migration and absorbs no Phase 11 work.
   `staleAfterMs` continues to come from `settings_versions.operational_stale_after_seconds`, as the
   accepted repository already reads it (`alert-repository.ts:159-163`).

   **Counter-evidence, disclosed.** `packages/api/src/alerts/types.ts:22-27` documents both fields
   as "Settings-derived", and `RESEARCH.md:617` records the reset buffer as settings-driven and
   owner-configurable. That is real evidence for the settings-column reading, and it is why this is
   recorded as an adjudication rather than a detail. It is outweighed here because `SPEC.md:595`
   labels the two 30-minute values `[Resolved here — defaults]` rather than owner-configurable,
   `SPEC.md:532` scopes the settings table to "timezone, hours, capacity, thresholds", and
   `PHASES.md:275-276` gives `phase11-settings` capacity, thresholds, schedule, business-day, reset,
   and freshness — alert policy appears in none of the three. If a human prefers the settings
   reading, say so before activation: it adds a coordinator migration lane and a Stage 0 to this
   plan, and is far cheaper to decide now than after Stage C.
2. **Retention cutoff arithmetic — day-quantized.** `SPEC.md` says "~12 months" — approximate by
   its own wording. This plan freezes it as: **quantize `now` down to the start of its UTC day,
   subtract twelve calendar months, and delete rows whose governing timestamp is strictly older
   than that instant.** Retention is not a business-day concept, so ADR-004's gym-local
   business-day machinery does not apply; UTC storage is authoritative. Governing timestamps:
   `audit_log.created_at`, `edge_health_log.occurred_at`, `alert_log.sent_at`.

   Quantization is load-bearing, not cosmetic. A `now`-relative cutoff advances every minute, so
   every minutely invocation would find newly-expired rows and no data-derived gate could make a
   repeat run a no-op — forcing either a persisted run marker (a new table or column, which is this
   plan's own immediate stop condition) or in-process memory (which is not durable across
   serverless invocations). A day-quantized cutoff is constant for the whole UTC day, so the first
   invocation of the day deletes and every later invocation that day is inherently a no-op. This is
   what lets retention run on every invocation with no persistence, no gate, and no migration.
3. **Handoff directory.** `docs/phase-records/handoffs/phase8-integration/`, matching the
   `phase8-alert-evaluator` slice-named sibling rather than the aggregate-named `phase-7` directory
   the Phase 7 integration slice happened to use.
4. **Composite-runner failure contract.** Each component runs in fixed order on every invocation;
   a component failure is captured and does not prevent the remaining components from being
   attempted; after all attempts, an aggregate error is thrown so the cron seam returns its existing
   `500`/`no-store` and logs only the error name. This is chosen so an alerting fault can never
   silently suppress the scheduled reset, and vice versa. Frozen here and proved by a required test.
