## The slice's central risk, resolved empirically

The risk carried since stage 1: mounting the section introduces an `admin.access.list` request into
five sibling `/admin` specs that stub no such route, and **repairing those specs is forbidden to this
slice**.

It was resolved by running them, not by assuming. The first run **failed 3 of 31** — and the failure
mode was not the one predicted.

### The coordinator's first mount decision was wrong

`enabled` was initially passed unconditionally true, on the reasoning that gating on the shared
analytics query would be cargo cult because access has no timezone dependency. **That reasoning was
wrong**, and the specs caught it.

`apps/web/src/hooks/use-owner-health.ts:29-36` documents the gate, and it has nothing to do with
timezone:

> While that shared query is pending or failed the section is `unavailable` and renders nothing.
> `/admin` is then already announcing exactly one "loading" status, or showing exactly one error with
> one retry, for the same transport; a second copy would be a competing announcement for a screen
> reader and a duplicate control for everyone else (`DESIGN_GUIDE.md` §13).

So the three failures were `getByRole('status')` and `getByRole('alert')` each resolving to **two**
elements — the sibling's region plus a second one from the access section. That is not locator
brittleness. It is the sibling specs correctly detecting a **real accessibility regression** against a
binding design authority. Stage 1's Risk 4 named "the one-live-region convention" explicitly and the
coordinator under-weighted it.

Failing specs: `phase11-shell.browser.spec.ts:340`, `phase9-owner-ui.browser.spec.ts:292`, and
`phase9-owner-ui.browser.spec.ts:365`.

### The fix, and why it went where it did

The section now derives its own stand-down from the shared prerequisite, mirroring health exactly:
`enabled && !analytics.isPending && !analytics.isError`.

It was placed in `owner-access-section.tsx` rather than in the route deliberately. `/admin` renders
its forbidden branch from the same component, so a route-level `useOwnerDailyAnalytics()` call — which
the rules of hooks require to be unconditional — would fire the shared query for a caller who is not
allowed to see the page at all, and would put a new request into the shell's forbidden-state test.
Placing the gate in the section matches where audit and health put theirs, keeps `admin.tsx` a pure
two-line mount inside the lease, and leaves the forbidden path untouched.

**No sibling spec was edited.** The stop condition was not reached.
