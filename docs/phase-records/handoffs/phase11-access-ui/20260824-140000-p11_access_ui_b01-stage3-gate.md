## What the stage got right that the brief did not ask for

- **`<bdi dir="ltr">` around the revealed PIN** (`owner-access-view.tsx`). A numeric credential inside
  an RTL run can reorder visually; a bidi isolate is the correct fix. The brief never mentioned it.
- **Focus return captured at invocation, not at mount.** `returnFocus` is taken from
  `document.activeElement` when the provision/rotate trigger fires, so a pending mutation that blurs
  its own button cannot drop focus to the body when the reveal is dismissed.
- **A native `<button>` for the dismiss control**, because the shared `@fitway/ui` `Button` wrapper
  drops the `ref` prop — a real constraint discovered and worked around correctly rather than papered
  over.
- **The reveal is a non-modal `role="dialog"`** with `aria-labelledby`/`aria-describedby`, so
  announcing it does not make a screen reader re-read the owners list.

## Finding against the installed workflow tooling, not against FITWAY

Closing this gate turned the `agent-project-workflow` registry regression harness red:
`scripts/resolve-opencode-worker.mjs --validate` went from 65 passed / 0 failed to 64 / 1. The
failing scenario is `reuse-survives-outcome-recorded-before-the-decision`.

**The resolver behaved correctly and the FITWAY data is correct.** The scenario is coupled to the
live, mutable `evidence/ox-alpha.json` record rather than to a frozen fixture. Its stored decision is
dated `2026-08-22T09:00:00Z`, and its whole purpose is to prove that an adverse outcome recorded
*before* that instant does not trigger requalification. That held only while `ox-alpha`'s newest
adverse entry was the finalization truncation of `2026-08-22T01:05:00Z`. The two
`FAILED_TRANSPORT` entries this stage recorded — `2026-08-24T13:37:30Z` and `2026-08-24T13:44:00Z` —
are the first adverse entries to post-date the fixture's cutoff, so the resolver now correctly
reports `route_evidence: requalified` where the scenario asserts `reused`.

The harness therefore penalizes exactly the behaviour the workflow requires: recording an adverse
outcome before rerouting. Any real `ox-alpha` failure recorded after 2026-08-22T09:00:00Z breaks it.

**Deliberately not repaired here.** The skill lives outside this repository, the fix belongs to
whoever owns that tooling, and editing a regression harness so it goes green is the wrong instinct in
any case — a red test caused by correct data is a finding, not a chore. It is recorded so a later
session does not misread the red harness as a FITWAY defect, or worse, "fix" it by deleting truthful
evidence entries.

It does not block Slice B: every route decision in this run was resolved correctly, and
`scripts/verify-repository.mjs` and `pnpm verify:fast` are both green.
