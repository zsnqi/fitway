## 3. Locked domain boundary

### 3.1 Editable settings

The client may submit only:

1. `capacity`;
2. `thresholds.quietMaxPercent`, `thresholds.moderateMaxPercent`, and `thresholds.busyMaxPercent`;
3. `weeklySchedule` with exactly `sun`, `mon`, `tue`, `wed`, `thu`, `fri`, and `sat`;
4. `businessDayBoundary`;
5. `resetBufferMinutes`.

These are five product axes; the three threshold numbers form one axis.

### 3.2 Read-only operational settings

The read response shows, and every update copies forward from the locked current row:

- `timezone`;
- `pushIntervalSeconds`;
- `freshForSeconds`;
- `operationalStaleAfterSeconds`;
- `publicPollSeconds`.

They have no enabled form control and no update-input field. Defaults are not substitutes for stored values. Omitting these columns on insert would incorrectly reapply database defaults and is a correctness failure.

### 3.3 Server-owned metadata

The following never appear in update input:

- new `version`;
- `effectiveFromUtc`;
- `createdAt`;
- `createdBy` / actor identity;
- audit identity or audit action;
- operational timing values;
- an audit reason.

`expectedVersion` is concurrency metadata, not an editable setting. It must equal the version the owner read.

### 3.4 Reason decision

The conceptual audit model permits an optional reason; it does not require one. The accepted Paper form contains exactly five editable axes and no reason control. Therefore Settings update passes `reason: null` to the existing audit builder. Adding a reason field would be a sixth unauthorized input and requires a new human decision.

## 4. Canonical shared contract

All Zod objects are strict: unknown keys fail rather than being stripped. Numbers are JSON numbers, finite integers, and safe integers.

```ts
type Weekday = "sun" | "mon" | "tue" | "wed" | "thu" | "fri" | "sat";

type DailyHours = {
  open: string;  // exactly HH:mm, 24-hour Western digits
  close: string; // exactly HH:mm, 24-hour Western digits
};

type EditableOwnerSettings = {
  capacity: number;
  thresholds: {
    quietMaxPercent: number;
    moderateMaxPercent: number;
    busyMaxPercent: number;
  };
  weeklySchedule: Record<Weekday, DailyHours | null>;
  businessDayBoundary: string; // exactly HH:mm
  resetBufferMinutes: number;
};

type OperationalOwnerSettings = {
  timezone: string;
  pushIntervalSeconds: number;
  freshForSeconds: number;
  operationalStaleAfterSeconds: number;
  publicPollSeconds: number;
};

type OwnerSettingsSnapshot = {
  version: number;
  effectiveFromUtc: string; // RFC 3339 / ISO UTC instant
  editable: EditableOwnerSettings;
  operational: OperationalOwnerSettings;
};

type OwnerSettingsReadOutput = OwnerSettingsSnapshot;

type OwnerSettingsUpdateInput = {
  expectedVersion: number;
  editable: EditableOwnerSettings;
};

type OwnerSettingsUpdateOutput = {
  settings: OwnerSettingsSnapshot;
  auditId: number;
};
```

The public leaves are exactly `admin.settings.read` and `admin.settings.update`. Both use the existing `ownerProcedure`: unauthenticated/expired sessions are `401`; authenticated staff are `403`. Actor identity comes only from `context.auth.principalId`.

## 5. Validation and time semantics

- `expectedVersion`: positive safe integer.
- `capacity`: integer `1..2_147_483_647` (the existing PostgreSQL integer/storage boundary). No invented lower ceiling and no validation against current occupancy.
- thresholds: integers with `0 <= quiet < moderate < busy <= 100`.
- `weeklySchedule`: exactly seven known keys. A closed day is `null`; an open day is exactly `{ open, close }` with no extra keys.
- wall times and boundary: canonical `HH:mm`, `00:00..23:59`, Western digits. Database `HH:mm:ss` values normalize to `HH:mm` at the API boundary.
- schedule session semantics reuse [`resolveScheduleSession`](../../../../packages/api/src/occupancy/schedule.ts): `close > open` closes the same civil day; `close <= open` closes on the following civil day. Equal open/close therefore represents a 24-hour session, not a closed day.
- `resetBufferMinutes`: integer `0..2_147_483_647`.
- stored schedule pairs must be both null or both present. An impossible partial pair or malformed stored value is an internal invariant error; it is never repaired with a default.

Do not invent cross-day overlap checks, a maximum reset buffer below the storage limit, a relationship between the boundary and opening hours, a capacity/current-count rule, or a no-op rejection. A valid no-op request is still a valid append-only mutation, although the UI disables Save while clean.

## 6. Current-effective resolution

The Settings surface defines current settings as the greatest row ordered by `(effectiveFrom DESC, version DESC)` whose `effectiveFrom <= capturedServerNow`. This is the repository's existing effective chronology and preserves equal-time version ordering.

- Capture one server-owned instant after obtaining the Settings advisory transaction lock. Use an injected application clock or PostgreSQL `clock_timestamp()`/equivalent; do not use a transaction-start timestamp captured before waiting for the lock.
- Read and update use this current-effective rule.
- If no effective row exists, return a generic internal invariant failure. Do not seed, infer, or apply schema defaults.
- The update creates `effectiveFrom = createdAt = capturedServerNow`, so it is immediately effective.
- Future scheduling is unsupported: there is no client `effectiveFrom` and no scheduling UI.

Existing consumers are not uniformly future-date-aware, but Settings cannot create a future row. Do not broaden this slice into a retrofit of unrelated readers. Pre-existing future-dated data is latent operational debt outside this contract.

## 7. Atomic update and concurrency algorithm

`admin.settings.update` executes this sequence inside one database transaction:

1. Acquire `pg_advisory_xact_lock(hashtext('fitway-phase11-owner-settings'))` or an equivalently fixed, Settings-only transaction lock.
2. Capture server time once, after lock acquisition.
3. Read the current effective settings row with the rule in section 6.
4. If absent, throw an internal invariant error.
5. Compare its version with `expectedVersion`. On mismatch, abort before any insert with the stable conflict described in section 8.
6. Insert one complete `settings_versions` snapshot:
   - values for the five editable axes come from validated input;
   - all five operational settings copy from the row read in step 3;
   - `effectiveFrom` and `createdAt` are the captured instant;
   - `createdBy` is the authenticated owner principal ID;
   - the database generates `version`.
7. Read back and validate the inserted row and generated JSON-safe positive version.
8. Build the existing audit entry with `buildSettingsAuditEntry({ actorPrincipalId, settingsVersion, reason: null, createdAt })`.
9. Append it with `appendAuditEntry` on the same transaction and capture its positive `auditId`.
10. Commit and return the inserted snapshot plus `auditId`.

Any failure from steps 3–9 rolls back both settings and audit. Never catch a database/audit failure and return partial success. The advisory lock plus `expectedVersion` ensures two owners starting from one version produce one success and one conflict, not two silently ordered successes.

## 8. Error contract

| Condition | Transport | Stable data/code | Detail policy |
| --- | --- | --- | --- |
| Missing/expired session | 401 | existing owner guard | existing non-enumerating behavior |
| Authenticated staff | 403 | existing owner guard | existing role behavior |
| Zod/type/range/order/time/unknown-key failure | 400 `BAD_REQUEST` | normal validation issue | field-safe detail only |
| `expectedVersion` differs after lock | 409 `CONFLICT` | `settings_version_conflict` | localized UI copy; no row contents in error |
| Missing settings history, malformed stored row, insert/audit failure | 500 | none exposed | generic owner message; internals only in server observability |

The update procedure may map only the typed Settings conflict to `CONFLICT`. Unexpected errors remain 500. Error messages must not echo full input, SQL, audit internals, or principal data.

## 9. Repository and consumer invariants

- No database/schema/migration/seed change.
- The inserted row is a full snapshot; append-only history remains intact.
- A successful update is visible to the Settings read and existing current readers on their next fetch.
- Historical `occupancy_minutes.capacity_snapshot` and `settings_version` remain immutable. Analytics/reporting continue resolving historical settings by recorded version/effective chronology; later Settings updates cannot rewrite past results.
- Reset scheduling continues to freeze the close-owning version through close plus buffer; Settings does not rewrite an existing issuance or historical decision.
- Current public output may change only in the already-authorized categorical band/open schedule/freshness behavior. It must never expose capacity, a denominator, thresholds, percentages, reset data, timezone configuration metadata beyond its existing contract, actor, or audit data.
- Edge/OpenAPI response shape remains frozen; no new Settings field is added there.
- Health/alert timing fields copy forward exactly. No Settings update resets them to defaults.

## 10. UI composition and interaction contract

- Accepted Paper controls the Settings section composition. Repository runtime may extend vertically to coexist with prior sections, but must not proportionally shrink, crop, or restyle the accepted form.

### 10.2 Required groups and order

The form contains:

1. route/section introduction and current version metadata;
2. capacity;
3. Quiet, Moderate, Busy threshold group;
4. seven-day weekly-hours group;
5. business-day boundary;
6. reset buffer;
7. visibly subordinate locked operational timing group;
8. predictable lower action row on long/mobile composition.

English reads LTR. Arabic content reads from the RTL start. In Arabic, threshold visual order from the reading start is Quiet → Moderate → Busy, and desktop weekly columns are Day → Opens → Closes → State. Do not reverse data order blindly. Latin values such as `Asia/Riyadh`, `20 s`, version identifiers, and Western digit/time runs use bidi isolation.

### 10.3 Form state machine

| State | Required behavior |
| --- | --- |
| standby | render nothing and issue no Settings request until the owner route/prerequisite allows it |
| initial loading | one section skeleton/status; no enabled form; do not duplicate the route's existing loading live region |
| load failure | no fabricated/default settings; generic error and one focused Retry action |
| clean | server snapshot populated; Save and Discard disabled; version visible |
| dirty valid | Save and Discard enabled; unsaved state visible in text, not color alone |
| dirty invalid | persistent labels and field/group errors; Save disabled; Discard enabled; focus moves to or is programmatically associated with the first invalid field on submit attempt |
| saving | one request only; all editable controls and both action rows locked; visible/assistive saving text; no frozen-spinner-only state |
| saved | replace baseline and expected version from returned server snapshot; clear dirty state; announce localized saved-version confirmation through one polite status region |
| atomic failure | preserve draft and expected version; unlock valid Save for retry; announce generic failure; do not claim any field was saved |
| version conflict | preserve draft, disable Save, state that settings changed elsewhere; the existing Discard action reloads latest server values and clears the conflict; never silently rebase or overwrite |

Switching locale must preserve current loaded data and draft. Navigating away with dirty data is not specified as a custom browser prompt and must not add one without authority.

### 10.4 Actions

- Save uses the current baseline version as `expectedVersion` and submits the entire validated editable snapshot.
- Discard never mutates. Normally it restores the last server snapshot locally. In conflict state it refetches the current snapshot and then restores that baseline.
- The upper desktop action/version row and the lower long/mobile dirty action row represent the same form actions. There is one form submission controller; duplicate visual buttons must not create duplicate requests.
- No Reset-to-defaults, scheduling, import/export, destructive confirmation, or audit-reason action.
