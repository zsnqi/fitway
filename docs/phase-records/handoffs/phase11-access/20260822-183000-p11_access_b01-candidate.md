## Two design decisions taken from the code, not from preference

**Deactivation revokes session rows; it does not rely on the checks that already exist.**
`AuthService.#resolveCookie` already refuses a session whose principal is inactive, whose credential
is inactive, or whose credential version moved. That ends a session *while* the principal is
deactivated, but the row survives, so reactivation would hand the principal its pre-deactivation
sessions back, still valid. The locked decision says deactivation invalidates active sessions. The
rows are therefore revoked, and the integration test asserts the old cookie stays dead after
reactivation while a fresh login succeeds.

**The last-active-owner count is read with the owner rows locked, before the target is examined.**
Without `for update`, two concurrent deactivations each read two active owners, each pass, and the
gym is left with none. The integration test fires both directions simultaneously and asserts exactly
one owner survives.

## Deviations from the slice plan, recorded

1. **The plan said extend `AuthRepository`; the candidate adds a separate `AccessRepository`.** The
   login contract is frozen and had no reason to widen. This narrows the surface the slice touches.
2. **`apps/server/src/access-service.ts` and `apps/server/src/auth/runtime.ts` were added to
   `ownedPaths` mid-slice**, and `packages/api/src/context.ts` to the shared lease. Both were
   recorded in the ledger before the edit, not discovered afterwards, each in its own commit.
3. **The exposed pepper is optional rather than required.** Making it required broke type checking in
   eight other milestones' integration tests, which build an `AuthRuntime` literal. Editing eight
   files this slice does not own to satisfy a type is scope creep; the optional member with an
   env-derived fallback keeps production on a single matching pair, and a hand-assembled mismatch
   fails as a rejected credential rather than a weaker one. The access integration test supplies the
   pepper explicitly and asserts that a generated PIN logs in through the real route, which is what
   proves the pair matches.
