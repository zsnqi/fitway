## The six b01 findings, and how each was closed

1. **Locking.** `lockPrincipalRow` takes `for update` on the target principal before the state read,
   used by `provisionStaffPin`, `rotateStaffPin`, `deactivateStaffPin`, `reactivateOwner`,
   `resetOwnerCredential`, and additionally by `deactivateOwner` after its existing count lock.
   The lock is on the principal row, not the joined read, because Postgres refuses `for update` on
   the nullable side of an outer join; every credential here is reached through its principal, so
   serialising the principal serialises the credential. `countActiveOwnersForUpdate` now orders
   before locking so concurrent deactivations queue rather than deadlock.
2. **The `appendGovernanceRow` comment** now separates the two guarantees it conflated: the
   server-side snapshot stops an inventing caller, the lock stops a concurrent one.
3. **`resetOwnerCredential` refuses a deactivated principal** through
   `assertOwnerCredentialResetAllowed`, with `owner_already_inactive`. Self-reset stays allowed; only
   self-*deactivation* is refused, and nothing locked makes an owner unable to change their own
   password.
4. **Three state refusals moved off `staff_pin_shape`** onto `staff_pin_already_active` and
   `staff_pin_not_active`. No transport change was needed — `rethrowAsTransportError` maps any
   `AccessRuleError` code — and no consumer exists yet, so this is additive.
5. **`assertStaffPinShape` is called on the generated PIN** in `createAccessService`, at the one seam
   where a PIN becomes credential material. The b01 candidate record's claim that the SPEC rule
   "lives in" `isStaffPinShape` was inaccurate; it is now true.
6. **Concurrency tests for every mutation**, below.

b01 finding 5 (concurrent provisioning surfacing as an untyped 500) was not on the successor list
but is closed as a consequence of item 1: the case where no principal exists yet has no row to
lock, so the unique index arbitrates and the loser's violation is mapped to the same refusal the
locked path gives.

## The concurrency tests, and their negative control

Six new tests in `describe("every mutation under concurrency")` plus one that must run first,
`describe("the provisioning race before a shared staff principal exists")` — the only state in
which an unlockable provisioning race is reachable is the one `beforeAll` leaves, and once audit
rows reference the staff principal it cannot be deleted.

The shared discriminator: a lost update is invisible in the final row and loud in the sequence.
Two unlocked rotations both read version N and both write N+1, so the credential ends plausible
and the audit history is a lie. The assertions therefore read the versions each mutation *reported*
and the rows each *appended*, not the row that happens to be there at the end.

**Negative control, measured not asserted.** With the six locks, the credential-reset rule, and the
unique-violation mapping removed (run `p11_access_b02_n1`), five of the six fail on exactly the
defect each targets:

| Test | Failure without the repair |
|---|---|
| staff PIN rotation | `each rotation must claim its own version: expected 2 to be 3` |
| staff PIN deactivation | `expected [200, 200, 200] to have a length of 1 but got 3` |
| owner reactivation | three `owner_reactivated` rows for one transition, `expected […(3)] to have a length of 1` |
| owner credential reset | `each reset must claim its own version: expected 1 to be 3` |
| reset on a deactivated owner | `expected 200 to be 400` |

The sixth — the provisioning race before the principal exists — did **not** fail in that run,
because the three requests serialised naturally on a warm database. Its negative control came from
a different run instead, and is stronger: on cold database `p11_access_b02_r3` it failed with
`a lost provisioning race is a refusal, not a server fault: expected 500 to be 400`, because
`isUniqueViolation` checked the top-level error while Drizzle keeps the `pg` error underneath as
`cause`. The mapping had never matched. It now walks the cause chain under a depth bound. That is a
real defect in the b02 repair, found by this suite before submission, and it is recorded here rather
than quietly fixed.

That failure also exposed a fixture problem: the provisioning race restored state at the end of its
test body, so its failure left an active PIN and broke a later block. The restore moved to
`afterAll`, so a failure there reports itself instead of cascading.

## What a verifier should attack

Stated plainly, because a verifier that only reruns these commands learns only what they already
say:

1. **Whether the principal lock is genuinely sufficient.** The claim is that every credential is
   reached through its principal. A path that touches a credential row without going through the
   principal would break it.
2. **Deadlock under mixed traffic.** `deactivateOwner` takes a set lock then a row lock; the others
   take one row lock. The ordering argument is in the code comments; it has not been tested under a
   mixed storm.
3. **Whether the `cause`-chain walk is right.** The depth bound is 5. A different driver wrapping
   could put `23505` deeper or expose it differently.
4. **Whether the concurrency tests are real for the right reason.** Five have a measured negative
   control; the sixth's control came from an unplanned cold-database failure, not a designed one.
5. **The eleven locked 2026-08-11 decisions**, all of which the b01 verifier marked HELD on the
   carried code. The b02 diff should not have moved any of them — that is a claim to check, not to
   accept.
